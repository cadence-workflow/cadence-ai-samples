# Incident Triage laptop measurements

Measured November 2, 2026. Review and follow-up: [Issue #158](https://github.com/cadence-workflow/cadence-ai-samples/issues/158).

Incident Triage passed 30/30 exercise scenario runs on an M4 Max, 64 GiB Mac. Three additional Qwen review runs with the one-line #117 patch passed. The useful follow-ups are model context and effective timeout behavior: the smaller Llama download allocated more memory, and history timeout fields differed from the Python option name.

This records completed synthetic local testing for review of #116, #117 and the ContribFest setup guidance. It is not an attendee exercise or a claim that 16 GB laptops are supported by these results.

## Revision timeout evidence

| Source | Model | First revision scheduled-to-completion, runs 1/2/3 | Recorded start-to-close | Recorded schedule-to-close |
| --- | --- | --- | --- | --- |
| #116 | qwen2.5-local | 5.701 / 6.510 / 6.759 s | 30s | 720s |
| #116 | llama3.2-local | 2.678 / 1.795 / 1.664 s | 30s | 720s |
| #117 | qwen2.5-local | 10.687 / 8.611 / 8.876 s | 180s | 720s |

All first revisions completed at attempt 0. No revision timeout occurred. The #117 comparison applies only its `QUICK_ACTIVITY` to `MODEL_ACTIVITY` change to the same #116 checkout. It is not a performance optimization or a randomized speed comparison.

The source option is named `schedule_to_close_timeout`. SDK 0.4.1 fills omitted start-to-close and heartbeat values from it. The effective retry-enabled histories record the fields above. Investigate server retry normalization before describing 30 seconds as an overall retry budget. Preserve this distinction in documentation and review of #117.

## Model memory and setup

- Qwen `qwen2.5:7b`: 6.15 GiB native Ollama allocation, all reported on Metal, context 32,768 tokens. Download: 352.102 s, 4,683,087,332 layer bytes.
- Llama `llama3.2`: 16.54 GiB native allocation, all reported on Metal, context 131,072 tokens. Download: 156.299 s, 2,019,393,189 layer bytes.
- Default contexts were left unchanged. Model download size does not establish runtime memory. These results do not support recommending Llama as a 16 GB fallback under these defaults.
- AC power, 16 logical CPUs, macOS 26.7.1; existing Docker/Kubernetes workloads stayed running. Ollama v0.40.13 used Metal. Official binary checksum verified before execution. No paid inference.
- Runtime download: 19.773 s. Recipe dependency setup from public PyPI: 8.732 s after a separately recorded authenticated-mirror failure. No credential-bearing output is included here.
- Cadence was already running; its cold startup was not measured. DescribeDomain succeeded over the SDK. Existing services were not reconfigured.
- Substantial swap existed before testing. Before/after swap usage did not increase across any measured batch. Point-in-time system memory readings are not a continuous peak measurement.

## Validation and reproduction

The actual runner was `recipes/incident-triage/python/bare/exercises/retry_policy_live/run_exercise.py`, with `--scenario all --cleanup reject --model-id <model> --options <local-completed-policy> --target <local-grpc-address> --web-url <local-web-address> --evidence <new-directory>`. Repeat three times for each model. For the #117 comparison, apply only its verified one-line patch and run Qwen with `--scenario review` three times.

Recipe unit tests: 28 passed on #116 and 28 on the comparison checkout using `python -m unittest discover -s tests -v`. A sandboxed comparison invocation could not bind its HTTP test fixture; the loopback-enabled rerun passed. Full logs, histories, model receipts and allocation samples are retained privately by the reporter. This report contains aggregate measurements. Private fixtures, raw histories and attendee solutions are excluded.

Runner pass checks cover retries, guards, revision/guidance behavior, receipts and cleanup. They do not establish diagnosis quality. Qwen inferred an overwhelmed ledger without evidence of why the pool was exhausted; Llama produced verbose, sometimes truncated hypotheses. Do not equate a completed Workflow with a verified root cause.
